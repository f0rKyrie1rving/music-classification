# 自动改进阶段的数据边界

核查日期：2026-09-27。本文件记录只读审计结果，以及本轮自动推进的先后顺序。
本次仅读取既有清单、冻结记录和本地官方元数据；没有下载、索引、抽取特征或预测新歌曲。

## 本轮先做什么

先用原有 **1,206 首／469 位艺人**的开发池做按艺人分组的嵌套交叉验证。
候选方法和筛选门槛应在运行前写清；拟合、校准和阈值选择只能使用各自允许的内层数据。
外层结果用于本轮开发筛选，不能把相互重叠的划分当成独立数据集做普通 t 检验。
这个开发池已有大量历史实验，因此其结果仍是开发证据，不是新的独立确认。

**只有开发门槛通过，才固定最终候选和新歌验证方案，再开始新歌的索引、抽样和获取。**
若门槛未通过，本轮不启动新歌验证。不得通过不断换一批新歌，直到得到有利结果。
现在没有启动 12–19 分片的音频获取，也没有从该范围选定具体歌曲。

这一阶段可完全自动完成，无需人工听辨作为前置条件。目标仍是预测既有来源标签；
这些标签是有噪声、可能不完整的代理标签。自动优化和验证不能确认某首歌确实漏标，
也不能代替人的音乐风格判断。不得自动把当前误报改成正标签。

## 资源估计与技术失败

以已经完成的两轮为参考：

- 04–07 成功处理 266 首，编码缓存合计 105.43 MiB；MAEST 特征提取约 277 秒。
- 08–11 成功处理 204 首，编码缓存合计 81.00 MiB；特征提取约 188 秒；
  另有 28/232 首因 DNS 问题失败。

因此，约 371 首的量级可暂按约 **150 MiB 编码前缀、470 MiB WAV、3.3 MiB 特征**
及 **6–7 分钟 CPU 特征提取**规划，另加模型初始化和来源核验。
按旧单曲上限 1.25 MiB 计算，编码前缀预算上界约 464 MiB，不能把均值当硬上限。
八个 TAR 分片还需要数千次很小的头部范围请求，带宽不大，但网络往返会影响耗时。
以上是基于本机旧运行的估计，尚未检查新分片的在线可用性。

网络是主要时间不确定性：前一轮冻结到下载记录约 13 分钟，后一轮约 94 分钟且有
DNS 失败；这些阶段耗时不等同于纯传输时间，不能据此承诺下一轮完成时间。
若发生新的技术故障，应遵守下一份预先固定的恢复／失败规则，不修改旧失败记录，
不选择性重试看起来容易得到好结果的歌曲，也不静默补歌。
